1

Create a branch

GitHub
A collaboration platform that uses Git for versioning. A popular place to share and contribute to open-source software. (Course video: What is GitHub?)
Repository
A project containing files and folders. A repository tracks versions of those files and folders.
Branch
A parallel version of your repository. By default a repository has one branch, main, which is the definitive branch. Creating another branch copies main so you can change things safely without disrupting the main project. People commonly use branches to work on a specific feature without affecting the rest. Branches keep everyone's work safe while you contribute.
Profile README
An "About me" section shown at the top of your GitHub profile page, where you share information about yourself with the community.

Your first branch

  1. Open your copy of the exercise in a second browser tab; work there while reading here.
  2. Go to the < > Code tab.
  3. Click the main branch drop-down.
  4. In Find or create a branch…, type my-first-branch (the exact name is checked).
  5. Click Create branch: my-first-branch from main. GitHub switches to the new branch automatically and the drop-down now shows its name.
  6. Wait for Mona's comment with the next lesson.
Having trouble?Make sure the branch name is exactly my-first-branch: no prefixes or suffixes.

Commit a file

Commit
A set of changes to the files and folders in your project. A commit exists in a branch. It records changes such as adding, removing or renaming files and modifying file content.
Commit message
A short summary of the change, with an optional extended description. Both give clarity, which matters most when a commit touches several files.
.md
The file extension for a Markdown file (covered fully in Course 3).

  3. Name the file PROFILE.md.
  4. Enter this content:
    Welcome to my GitHub profile!
  5. Click Commit changes… (top right). A dialog opens.
  6. Replace GitHub's suggested message with Add PROFILE.md.
  7. Ignore the other fields and click Commit changes.
  8. Wait for Mona.

Open a pull request

Pull request (PR)
Where collaboration happens. A PR shows the changes on your branch to other people and lets them accept, reject, or suggest further changes. In a side-by-side comparison it proposes applying your branch's changes to the main branch.
base vs compare
base is the branch you want to merge into (main); compare is the branch holding your changes (my-first-branch).

Create a pull request

After committing you may see a banner with a Compare & pull request button. Clicking it skips to item 5. To practise the manual route, use items 1–4.

  1. Open the Pull requests tab.
  2. Click New pull request.
  3. Select base: main and compare: my-first-branch.
  4. Click Create pull request.
  5. Set the title to Add my first file (by default it is your commit message).
  6. Write a short description: you created a branch, created a file, and made a commit.
  7. Click Create pull request.
  8. Wait for Mona.
Having trouble?Check the PR title is correct and that the PR has a description.

Merge your pull request

Merge
Adds the changes in your pull request and branch into the main branch. A merge is itself a kind of commit, which is why its dialog looks like the commit dialog.

Merge the pull request

  1. Click Merge pull request. If workflows are still running the button may be inactive; wait for them to finish.
  2. Click Confirm merge.
  3. Click Delete branch: once merged, the branch is no longer needed.

Introduction to Git version control

Scenario: backups have become hard to organise and everyone shares updates differently. Git replaces file-naming conventions, shared drives and emailed copies.

What version control solves

Backup and recovery · sandboxed experimentation · parallel development · locked files · file duplication · conflicting changes · team collaboration. Familiar symptoms:

my-project-final-v2-really3.zip
"When did that stop working? I didn't change anything!"
"The file is locked. I'll work on a copy until he gets back on Monday."
"Which email had v2 in it? I think the one from last Wednesday."
Distributed version control
Each developer has a complete copy of the project history, unlike centralised systems with one shared copy. Advantages: work offline (most operations are local); robustness (every copy is a backup); flexible workflows (each developer chooses processes and tools).
Where Git is used
CLI: the original tool and source of all functionality. Code editors: VS Code, JetBrains IDEs, Xcode, Emacs/Vim. Hosting services: GitHub, GitLab, Gitea, Azure DevOps, AWS CodeCommit, Bitbucket. Desktop apps: GitHub Desktop, Sourcetree, TortoiseGit, GitKraken, GitButler, and more at git-scm.com/tools/guis.
ImportantThe exercise runs on a machine with Git pre-installed. To install it yourself, use the guides at git-scm.com.

Working with branches

Questions this answers: how do I keep history tidy, keep incomplete work out of it, and work on several features or fixes at once?

Branch (in Git)
A lightweight pointer, like a label, to a specific commit. You work on a dependent version without influencing the original.
main
Usually the trusted working version and the first branch (historically master).
Feature branch
A safe, isolated space to develop without affecting the trusted version.
Merging
Combining changes from different branches.

Three merge strategies

StrategyWhat happensResult from A–B on main, C–D on feature
Fast-forwardThe new commits are moved onto the parent branch. Git's default for git merge when possible.A → B → C → D (one straight line)
Merge commitChanges are applied as a single new commit on the parent; the child branch stays in the network for traceability.A → B, feature C → D, then merge commit E on main
Squash mergeAll branch commits are collapsed into one new commit on the other branch.A → B → "C+D"
gitGraph
   commit id: "A"
   commit id: "B"
   branch feature
   commit id: "C"
   commit id: "D"
   checkout main
   merge feature id: "E"
CommandPurpose
git branch my-new-featureStart a branch from the current branch
git checkout my-new-featureSwitch the working directory to that branch
git mergeApply one branch's commits onto another (default: fast-forward)
TipGit 2.23 introduced git switch to simplify branch handling, e.g. git switch branch-name and git switch --create <branch>. You will see it more often.

Commit to a branch (CLI)

  1. git log --all --graph --oneline: history is perfectly linear.
  2. git branch fix-incomplete-high-score
git checkout fix-incomplete-high-score
  3. git branch --list
  4. In index.js line 41 add, then commit:
    let highScore = 0;
    git add src/index.js
git commit -m "Add new variable for tracking high score"
  5. At line 61 add, then commit with "Add loading of stored high score":
    // Load high score from localStorage
highScore = parseInt(localStorage.getItem("stackOverflownHighScore")) || 0;
document.getElementById("high-score").textContent = highScore;
  6. At line 313 replace updateScore, then commit with "Add logic to keep track of highest score":
    function updateScore() {
  document.getElementById("score").textContent = score;

  // Update high score if current score exceeds it
  if (score > highScore) {
    highScore = score;
    document.getElementById("high-score").textContent = highScore;
    localStorage.setItem("stackOverflownHighScore", highScore);
  }
}
  7. git log --all --graph --oneline: the feature branch is three commits ahead of main and marked HEAD.
  8. git checkout main
  9. Merge with "no fast-forward" so the branch stays visible in history:
    git merge --no-ff fix-incomplete-high-score -m "Fix high score tracker"
  10. git log --all --graph --oneline: the parallel branch is shown merged.
  11. git branch --delete fix-incomplete-high-score
    This removes only the name (label); the commits remain.

Learn about merge conflicts

Merge conflict
Occurs when changes are made to the same part of the same file on two different branches. It is common when working with others and need not be frightening.
gitGraph
    commit id: "Initial"
    commit id: "Add resume.md"
    branch my-resume
    checkout my-resume
    commit id: "Update skills"
    checkout main
    commit id: "Also update skills"
    checkout my-resume
    commit id: "Other changes"
    checkout main
    merge my-resume id: "Conflict!"
  1. The repository gets a resume.md.
  2. Branch my-resume updates the skills area.
  3. Meanwhile someone updates the same skills area on main.
  4. my-resume gains unrelated changes too.
  5. Merging my-resume into main conflicts: both changed the same part of resume.md.

Resolve a merge conflict

Git merges intelligently and asks a human only when the situation is unclear. You have three choices:

OptionResult
Accept the base branch versionKeep main's text

When to resolve
As soon as you notice. Resolving does not merge the PR. GitHub stores the resolution as a reverse merge commit: changes from base (main) are merged into compare (my-resume). Only the compare branch changes, so you can test the result and keep working before the real merge.

Leave a review

A review is feedback from collaborators or the community. It protects quality and momentum, and it is a way to learn the project and see how others solve problems. The best way to get one is to ask: assign a reviewer.

Review typeMeaning
CommentGeneral feedback, neither approving nor rejecting
ApprovePermits merging where rulesets, code owners or other policies require approval
Request changesThe work does not yet meet expectations; re-request a review after fixing

A typical review

  1. Check the title and description are clear and concise, and convey the change and any linked issues.
  2. Check Files changed matches the description.
  3. For most updates, try the change to confirm it works as intended.
  4. Follow the repository's contributing guide for review, testing and quality requirements.

Good review habits

Identify issues, risks and limitationsSuggest changes and improvements
Flag upcoming changes the PR does not account forAsk questions to confirm shared understanding
Say what the author did wellPrioritise the most important feedback
Be concise yet meaningfulTreat the author with kindness and empathy

Leave a review

  1. Open Files changed and review the change (a simple wording adjustment).
  2. Click Submit review above the diff.
  3. Comment Looks good to me. I think this is more intuitive. Nice work! and submit. You cannot Approve or Request changes on your own PR.
CautionDo not merge yet.
